## Deduplication rules

- `CONFIRMED` means the row is the primary representative of a surviving, missing canonical implementation unit.
- `DUPLICATE` means the row is valid but is another declaration, formatter, consumer, or UI facet of a canonical unit already counted once.
- `REJECTED` means false pair, already equivalent in TypeScript, later-hop/non-surviving, or performance-only.
- Cleanly UI/terminal, tools/permissions, or core/session rows remain owned by those domain reports and are not counted again here. Borderline remote, plugin, auth, settings, shell-runtime, and cron rows are included.

- **Later-hop/non-surviving:** proactive agent metadata, the temporary `setAppStateForTasks` forms, and the 101-only installed-manifest candidate loop remain excluded.
- **Cleanly owned elsewhere:** terminal clear/reset, search bar focus, CustomSelect DOM input, command suggestion identity/ranking, team creation, bridge worktree preservation, and classifier/image/session-state rows remain UI/Tools/Core units. They are not duplicated into this services count.
- **Warning handler rows (`Kz5`/`qz5`):** real but cleanly core runtime lifecycle, so they remain in Core ownership rather than being counted as a service integration unit.
- **Tool-not-available explanation:** despite living under `src/services/tools`, it is a clean Tools execution-path item and remains owned by the Tools report.

## Ordered implementation units and dependencies

1. **Environment primitives:** implement `U11` first. It supplies `OTEL_LOG_TOOL_CONTENT` routing for `U04` and consistent host management for CA behavior.
2. **CA/auth startup:** implement `U09`, `U10`, then `U08`. These are independent at runtime but all touch early startup/auth initialization and should be reviewed together for ordering/cycle safety.
3. **API client/error behavior:** implement `U05`, then `U01` and `U02`. `U01` should reuse one value-returning unified-limit parser rather than duplicate the existing header parser.
4. **Tracing privacy:** implement `U04` after `U11`. Gate only sensitive content; keep tool schema/hash metadata behavior that official 101 did not gate.
5. **Remote managed settings:** implement `U12` as one atomic unit across fetch validation, cached/inline loading, and security comparison. Partial landing would make the three stages disagree on filtered versus raw settings.
6. **Shell runtime:** implement `U13`; first extend `ExecOptions`/provider interfaces and call sites, then reorder temp creation before sandbox wrapping and set `CLAUDE_TMPDIR` only after successful creation/EEXIST.
7. **Plugin dependency model:** implement `U14` before plugin update consumers. Order: raw constraint schema/type -> loader preservation -> resolver comparison -> error union/formatters -> operation `skipped` result -> autoupdate handling.
8. **Plugin source/cache reliability:** implement `U15`, then `U16`; source classification determines when copying should happen, and the nested-copy guard remains defense in depth.
9. **Plugin execution/validation hardening:** implement `U18` and `U17`. These are independent of dependency constraints but share plugin test coverage and can follow the loader signature changes.
10. **Plugin UI propagation:** implement `U03` after service result contracts are stable; it is a small consumer-only change.
11. **Remote environment eligibility:** implement `U06` before `U07`. The visibility check should call the same eligibility semantics used by launch, avoiding a second divergent preflight.
12. **Teleport/remote lifecycle:** implement `U19`, then `U20`. Preserve typed errors before generic wrapping; update status/queue/disconnect handling without regressing later 108 notification handling.
13. **Ultraplan callbacks:** implement `U22` callback typing before `U21` status/meta propagation. `U21` needs a one-shot guard so repeated `plan_ready` polls do not spam.
14. **Cron scheduling:** implement `U23` independently, adding the default, validated schema field, and exact cache-boundary branch together.
